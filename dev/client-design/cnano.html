C-nano Client Design#

The internal design of the C-nano client. This page builds on the shared client design and the client specification. Usage is in the C-nano guide. Paths are relative to client/cnano/.

Service Stubs#

clientgen generates one header per service from cnano.tmpl in krpctools. Each function is static inline, so a header can be included from several translation units.

A stub calls by service and procedure id, and src/krpc.options removes the name fields. This keeps names out of flash and off the wire.

Each procedure also has a _call function, for server side functions. An unused one adds compile time and no code.

KRPC_DEPRECATED goes before a declaration, the one position GCC, Clang and MSVC share. An enumeration value takes KRPC_DEPRECATED_VALUE after its name, as the attribute has no other position there. MSVC has no such attribute in C, so the macro is empty for it.

Server Side Functions#

The stubs leave out internal procedures, so krpc_compile_function and krpc_run_function are written by hand in include/krpc_cnano/functions.h. They hold the ids of KRPC.CompileFunction and KRPC.RunFunction. clientgen adds krpc_list_nullable_bytes_t to the KRPC header, as no public procedure uses that type.

  • A run passes encoded bytes. C has no generics, so krpc_run_function takes no type. The program encodes the arguments and decodes the value at the types it knows.

  • A null value has no bytes. Decoding it fails at most types. It succeeds at a list or a tuple, which leaves the list empty and the tuple’s items unset, so the program checks isNull there.

  • A call message copies its arguments. A stub’s krpc_call_t borrows its arguments for the call. A krpc_schema_ProcedureCall outlives the _call function that fills it in, so each argument is encoded onto the heap, tag and length included. Encoding the message then writes those bytes as they are.

  • That code has its own file, src/procedure_call.c, so a static link without functions leaves it out.

  • There are no function streams or events, as the client has no streams.

  • A function names definitions by ids. The names would go in flash. The stubs define KRPC_CLASS_, KRPC_ENUMERATION_ and KRPC_STRUCT_ macros as the pair of ids, as for exceptions, which the ById procedures take. GetFieldByIndex names a field by its position, which a KRPC_FIELD_ macro holds, so a program never writes the number.

Errors#

Library functions return a krpc_error_t, one code per kind of error a program handles differently. A refusal has a code of its own, apart from the other connection errors, as a program retries a garbled handshake on a serial line and gives up on a refusal.

KRPC_CHECK applies only in the stubs and functions.h, where KRPC_ERROR_CHECK_ASSERT, KRPC_ERROR_CHECK_EXIT and KRPC_ERROR_CHECK_FN replace its return.

  • Transports keep their own codes. A transport’s functions, krpc_read and krpc_write return KRPC_ERROR_IO and KRPC_ERROR_EOF. A library function turns either into KRPC_ERROR_CONNECTION, with the transport’s code as the cause, so custom transports stay as they are.

  • One record holds the last error, as errno does. The client runs one session at a time on the calling thread, so one static record serves. A field that does not apply is -1, as KRPC_OK, the status OK and the reason CLOSED are real values. The ids are 0, which is never an id.

  • A server exception is told apart by its ids. Comparing the names would put them in flash. The stubs define KRPC_EXCEPTION_<SERVICE>_<NAME> as the pair, which KRPC_IS_EXCEPTION compares with the record.

  • One macro fills the record at each failure site. KRPC_FAIL takes a sentence, compiled only when the library keeps or prints messages. On AVR a kept sentence is a PSTR string, so it stays in flash.

  • A callback’s failure keeps its code. A nanopb callback returns only false, so it stores its code in krpc_callback_error. The function that ran nanopb returns that code in place of KRPC_ERROR_ENCODING. A null string argument thus returns KRPC_ERROR_ARGUMENT.

  • A cause’s message comes first and the sentence goes in front of it. A transport or the server gives the cause’s message before the library knows the failure. krpc_fail then moves the message along to put the sentence and a colon in front, cutting what does not fit.

The detail levels trade memory for what the program can tell:

The record is the default, as an Arduino sketch nearly always has its 16 bytes to spare. KRPC_ERROR_BUFFER_TOO_SMALL stays apart from KRPC_ERROR_ARGUMENT, as a program retries with a larger buffer.

A session ends on a failed read or write, a disconnect, an unexpected message and a message that fails to parse. A response with other than one result is an unexpected message. A session survives a server error and a return value that fails to decode, as those responses have been read in full. A result the client has no memory for is skipped to the end of its message, so the session survives that too. A request that fails to encode ends the session only once part of it has been written.

A null result returns no error code, as null is a valid value and the code would trip KRPC_CHECK.

KRPC_CHECK and KRPC_ALLOC_BLOCK_SIZE are read when the program compiles the stubs. KRPC_BUFFER_SIZE, the detail level and KRPC_CUSTOM_MEMORY_ALLOC are read when the library compiles. KRPC_ERROR_CHECK_FN is read by both.

Memory#

nanopb runs without its malloc support, and every variable-length field is a callback. A krpc_schema_Message therefore has a fixed size and lives on the stack. All heap memory goes through krpc_malloc, krpc_calloc and krpc_recalloc, which KRPC_CUSTOM_MEMORY_ALLOC replaces.

The caller’s variable selects the allocation, so the caller resets it before each call. A struct or tuple has no reset macro, so the caller zeroes it. KRPC_FREE_* frees one level.

A send encodes into its buffer with five bytes free in front, then writes the size prefix there, which avoids a sizing pass. A message that overflows is measured and encoded again, one buffer at a time. A receive asks the connection only for bytes of the current message, so a read never waits on a message that has not been requested.

Ownership#

krpc_connection_t is a value holding a transport pointer and a handle. A copy is the same connection, and the program owns it. The transport table must outlive it. No reference count exists, so a connection closes only as follows:

  • krpc_disconnect sends a disconnect if the session is live, then closes.

  • krpc_close closes with no message.

  • krpc_connect closes on a refusal, and on any failure over a non-resumable transport. Over a resumable one, other failures keep the line open for the program to retry.

A session that fails during a call leaves the connection open. Later calls return KRPC_ERROR_CONNECTION without using it, and krpc_disconnect then only closes.

Threads#

The client has no threads and no locks. Each call blocks its caller until the response arrives. Transport functions, nanopb callbacks and krpc_error_handler run on the calling thread.

Session state is in file statics in src/krpc.c: the next request id, whether the session has ended and whether a response has been read yet. krpc_connect resets them, so the client supports one open connection at a time. A program serializes all its calls, across connections too.

There is no timed read, so a POSIX or Windows call can block indefinitely. An Arduino read fails after the Stream timeout with no byte, which ends the session, so a sketch does not spin once the server goes away.

Transports#

A transport is a krpc_transport_t table, chosen at run time by the function that opens the connection. The platform decides at compile time which tables exist:

The program’s own

  • The run-time choice lets one build carry every transport. The vcpkg port needs this, as vcpkg features must be additive.

  • Each transport is one source file, so an unused one costs no code in a static link.

  • resumable means the link outlives the client. krpc_connect then skips a leftover message, and a call skips a connection_response before its first response.

  • The Arduino build is C++. krpc_open_serial is a template, as the serial classes of the cores share no base class with begin.

  • krpc_open_stream takes a Stream, the base class of HardwareSerial, SoftwareSerial and USB ports.
